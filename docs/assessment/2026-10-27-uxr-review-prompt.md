## 一、系统背景（用户视角）

- sz-orm 是面向**开发者**的数据库访问层库（非终端消费者产品）：72 个 workspace 成员（70 个 `sz-orm-*` 库包 + cli + examples），28 种 SQL 方言，21,134+ 测试。
- 目标用户（据既有产品评测与 README 定位）：Rust 后端团队、追求工程规范/质量门禁的团队、多数据库/国产库迁移团队、PHP/Laravel（ThinkORM）背景迁移者、普通 Rust 开发者。
- 用户可见资产：
  - **文档**：`README.md`（英文）/ `README.zh.md`（中文）、`docs/quickstart.md`（5 分钟快速开始，双路径：60 秒 SQLite 零依赖 / 约 5 分钟 MySQL/PG）、`docs/sz-orm使用指南.md`（约 3000+ 行中文指南）、迁移指南（`migration-guide-sqlx.md` / `migration-guide-diesel.md` / `migration-guide-seaorm.md`）、`query_builder_selection_guide.md`、`custom-diagnostic-guide.md`、`docs/glossary-zh-en.md`。
  - **快速开始**：`docker-compose.yml`（一键 MySQL+PostgreSQL）、`examples/src/bin/`（38 个可运行示例）。
  - **CLI**（`cli/`）：`make:model`、`make:migration`、`make:seeder`、`migrate`、`migrate:status`、`migrate:rollback`、`sql:validate`、`dialect list/show`、`info`。
  - **可视化/设计工具**：`sz-orm-designer`（ER 编辑器、索引设计器、代码生成、迁移生成、Web UI）、`sz-orm-studio`（开发者门户、服务端）。
  - **工程体系**：24 道质量门禁、覆盖率/变异门禁、审计证据链——这些是差异化卖点，但也可能成为新用户的认知负担。

## 三、研究方法（定性为主，三种数据严格分层）

**数据可信度分层（必须在报告中明确标注每处结论属于哪一层）**：

| 层 | 类型 | 标注 | 可信度 |
|---|------|------|--------|
| L1 | **事实证据**：文档/代码 `file:line`、真实命令输出 | `[事实]` | 可审计 |
| L2 | **研究者亲测**：你本人在本会话中真实执行 Quick Start/CLI/示例（dogfooding），记录真实输出、报错、耗时 | `[实测]` | 高（但仅代表研究者个体体验） |
| L3 | **模拟用户数据**：模拟访谈/焦点小组/可用性测试的合成回答 | `[模拟]` | 中低——**必须明确标注为合成数据，严禁冒充真实用户调查** |

**研究方法清单（按序执行）**：

1. **启发式评估**：用 Nielsen 10 原则 + DX 专项启发式（可发现性、一致性、错误恢复、文档可信度、可复现性）评估 README/quickstart/CLI 输出/错误信息。
2. **认知走查**：以「Rust 后端新手」画像走查 `docs/quickstart.md` 路径 B 全流程，逐步记录：用户目标 → 界面/文档提供的行动 → 用户能否识别正确操作 → 反馈是否清晰。找出每一步的认知断点。
3. **人物画像（Persona）**：构建 4~5 个典型画像：①Rust 资深后端工程师；②PHP/Laravel（ThinkORM）迁移者；③. NET/Java 团队评估者（习惯 EF Core/Dapper/MyBatis）；④追求工程质量规范的技术负责人；⑤普通 Rust 初学者。每个画像含背景、目标、痛点、技术熟练度、文档阅读习惯。
4. **用户旅程地图 + 情绪曲线**：从「发现 sz-orm」→「读文档」→「跑通第一个查询」→「写模型/迁移」→「集成测试/门禁」→「部署生产」的完整旅程，标注每阶段情绪（-2~+2），标记低谷点。
5. **模拟用户访谈（L3）**：设计半结构化访谈提纲（见附录），模拟访谈上述 3~4 位画像，产出带"引言语录"的关键发现。**必须标注「以下为模拟合成数据，用于说明研究方法与可能痛点，不代表真实用户意见」**。
6. **焦点小组（L3，模拟）**：主题「从现有 ORM 迁移到 sz-orm 的障碍」，模拟 5 人小组讨论，记录共识与分歧。
7. **可用性测试**：设计 5 个典型任务（见附录），设定完成标准与观察指标（完成率、耗时、挫败点、错误路径）。**优先由你亲自真实执行（L2）**；再模拟 2 名不同画像的被测者表现（L3），两者分开呈现。
8. **痛点优先级矩阵**：将收集到的痛点按「严重度（1-5）× 发生频率（1-5）」排序，输出优先级象限。

## 四、评测维度（UXR 视角）

1. **首次上手体验**：5 分钟目标是否真实可达（实测！）；Quick Start 双路径是否清晰；零依赖路径是否真的零依赖；docker-compose 是否开箱即用；首次报错是否可理解。
2. **文档质量**：Quick Start → 使用指南 → API 参考的导航是否顺畅；双语一致性（README vs README.zh vs 使用指南）；数字/版本/示例是否自洽（G18/G24 门禁守护下是否真的无矛盾）；代码块是否可复制即用；术语表是否覆盖高频词。
3. **API 易用性与心智模型**：Model 定义门槛（手写 `impl Model` vs derive 宏的取舍）；链式 QueryBuilder 对 ThinkORM 迁移者的熟悉度；类型安全 DSL 的学习曲线；与 SQLx/Diesel/SeaORM 的 API 心智差异。
4. **错误信息与调试体验**：错误类型是否可操作（`custom-diagnostic-guide.md` 是否落地到真实错误输出）；`sql:validate` 等诊断工具是否好用；编译期错误提示是否带修复建议。
5. **工具链与工作流**：CLI 的 `make:model` 生成质量（生成后还要改多少）；迁移流程是否顺滑；`sz-orm-designer`/`sz-orm-studio` 是否真实可用（还是壳）；与主流 IDE/编辑器生态的配合。
6. **迁移体验**：SQLx/Diesel/SeaORM 迁移指南是否让迁移者感到"被理解"；API 对照表是否完整；迁移陷阱（如事务模型、连接池语义差异）是否被预警。
7. **信任与采纳障碍**：单作者项目的风险感知；crates.io 版本与仓库的同步状态；生产案例（sz-pay）的可信度呈现；24 道门禁对用户是加分项还是噪音；中英文社区的可得性。
8. **可访问性与本地化**：中文主导是否排斥英文开发者；术语翻译一致性（如 workspace/连接池/迁移）；文档对屏幕阅读/搜索的可达性。
