## 1. 总体结论

### 判定：**不可投产（当前工作树状态）**

不是「差一点」，而是数据库语义层有**三类会让 DBA 半夜被叫醒的确定性缺陷**：

1. **静默数据失真（P0）**：PostgreSQL 下 `TIMESTAMP/TIMESTAMPTZ/DATE` 列读取**恒为 NULL**（写入是成功的，DB 里数据正确，ORM 读回来是空）；`NUMERIC(38,10)` 双向往返都会把小丢成 `.0`。这两条都属于「不报错、不告警、数据悄悄没了」。
   - 证据：实验 `decimal-probe` 输出 `(A) raw-exact write -> ORM read : Decimal("1234567890123456789012345678.0")`，`(A') DB truth via ::text : String("1234567890123456789012345678.0123456789")`；`(C') DB truth ts=Some("2026-10-28 12:34:56.123456")` 而 `(C'') ORM read ts=Null`。
   - 代码：PG 行解码只有 `"NUMERIC"` 分支走 `rust_decimal`（`packages/sz-orm-sqlx/src/any.rs:1562`），**没有 `"TIMESTAMP"/"TIMESTAMPTZ"/"DATE"/"TIME"` 分支**，未知类型兜底只能解 i64/f64/bool/String 全失败 → 落 `Value::Null`（`packages/sz-orm-sqlx/src/any.rs:1586` 的 `_ =>` 分支）。整改后现状见 R1：时间分支已补齐（`packages/sz-orm-sqlx/src/any.rs:1568` 起），未知类型改为报错。
2. **事务隔离级别在 MySQL 上 100% 失败（P0）**：`SET TRANSACTION ISOLATION LEVEL ...` 在 `BEGIN` **之后**才发送（`packages/sz-orm-core/src/transaction.rs:543`），MySQL 明确拒绝（`Transaction characteristics can't be changed while a transaction is in progress`），并且错误被包成 `CommitFailed` 直接返回、**不回滚已开启的事务**。SQLite 上同样语句直接语法错误。Oracle 上 REPEATABLE READ / SNAPSHOT / READ UNCOMMITTED 也是 `ORA-02179`。
3. **方言“支持”是名义的（P0/P1）**：`QueryBuilder` 分页硬编码 `LIMIT/OFFSET`（`packages/sz-orm-core/src/query.rs:2887`），Oracle 实测 `ORA-03049: SQL 关键字 'LIMIT' 在此语法中无效`；PostgreSQL 的 `insert_or_ignore` 生成 `INSERT OR IGNORE INTO "t"`，实测 `ERROR: syntax error at or near "OR"`；Oracle/MSSQL/Kingbase/达梦 的 `lock_for_update()` 返回成功但 **SQL 里没有 FOR UPDATE**（静默丢锁）。

### 允许的有限使用（若一定要碰生产）

仅在同时满足以下全部条件时，可作为**非核心、可丢失数据**的旁路库试运行：

- 数据库：**PostgreSQL**（不要用 MySQL 创建带显式隔离级别的事务；不要用 SQLite 承载并发写）；
- 表中不含 `TIMESTAMP/TIMESTAMPTZ/DATE/NUMERIC`（或这些列一律不通过 ORM 读取、不使用 `Value::Decimal`）；
- 不使用 `insert_or_ignore`/`upsert`/`lock_for_update`；
- 事务一律 `TransactOptions::default()`（`isolation_level = None`，见 `packages/sz-orm-core/src/transaction.rs:92`）；
- 连接池 `release` 后自行假定会话状态可能被污染（见 §3.3），业务侧禁用 `SET SESSION`/临时表/用户变量；
- 上线前逐条通过 §9 的 5 项 DBA 验收。

**这不是“有条件投产”，是“带着镣铐做只读旁路”。**

## 3. 分维度详解

### 3.1 SQL 生成正确性与方言保真（20%）

**亮点**
- 标识符引号按方言正确：MySQL `` ` ``、PG/SQLite/Oracle `"`、MSSQL `[]`（实验 `matrix` 逐族输出）。
- PG 占位符重写可用：`?` 会被重写成 `$n`，且跳过字符串字面量/注释/JSON 操作符（`packages/sz-orm-sqlx/src/any.rs:1573`、`packages/sz-orm-sqlx/src/any.rs:1659`）；实测 `PG query_with_params('?') -> OK rows=1`、`$1` 同样 OK。
- Oracle 占位符 `?`→`:N` 有实现（`packages/sz-orm-oracle/src/lib.rs:229`），Oracle 套件 10/10 通过。
- `Dialect::build_pagination` 本身对 Oracle/MSSQL 生成合法 `OFFSET ... FETCH NEXT ...`，对 Informix 生成 `SKIP/FIRST`、Firebird `ROWS 11 TO 20`（`matrix` 输出）。

**风险**

| 级别 | 问题 | 证据 |
|---|---|---|
| **P0** | `QueryBuilder` 分页硬编码 `LIMIT/OFFSET`，绕过方言分页实现 → Oracle/MSSQL 生成非法 SQL | `packages/sz-orm-core/src/query.rs:2887`、`packages/sz-orm-core/src/query.rs:2891`；实测 `oracle select: SELECT * FROM "eval_qb" WHERE "id" = ? LIMIT 10`，Oracle 报 `ORA-03049`（sqlplus 实跑） |
| **P0** | PostgreSQL `insert_or_ignore` 生成 `INSERT OR IGNORE INTO` → 语法错误 | 默认实现 `packages/sz-orm-core/src/dialect.rs:173`，PG 未覆盖；psql 实跑 `ERROR: syntax error at or near "OR"`，同一行 `ON CONFLICT DO NOTHING` 成功 |
| **P0** | `lock_for_update()` 在 Oracle/MSSQL/Kingbase/达梦/OceanBase 返回 `Ok` 但**不追加锁子句** → 业务以为有行锁，实际裸读 | `packages/sz-orm-core/src/query.rs:488`；实验输出 `oracle lock_for_update -> OK: SELECT * FROM "eval_qb" WHERE "id" = ?`（无 FOR UPDATE） |
| **P1** | Oracle/MSSQL 无 UPSERT；TiDB/MariaDB/Kingbase 等兼容库也被判为不支持 | `packages/sz-orm-core/src/query.rs:3035`；实验输出 `dialect Oracle does not support upsert`、`dialect TiDB does not support upsert`（TiDB 实际支持 `ON DUPLICATE KEY UPDATE`） |
| **P1** | `insert_or_ignore` 对 PG 族/DB2/达梦/金仓/雪片/Informix/HANA/Firebird 全量生成非法 `INSERT OR IGNORE`（只有 SQLite/MySQL 合法） | `matrix` 输出：`kingbase ... ioi=INSERT OR IGNORE INTO "t"`、`snowflake ... ioi=INSERT OR IGNORE INTO "t"` |
| **P1** | Snowflake 分页 `LIMIT 10, 10`（Snowflake 不支持逗号形式） | `matrix` 输出 `snowflake | paginate: SELECT * FROM t LIMIT 10, 10` |
| **P2** | GBase 归到 MSSQL 族（`[]` 引号 + OFFSET/FETCH），GBase 8a 实际 MySQL 兼容 | `packages/sz-orm-core/src/dialect.rs:1568` |
| **P2** | DuckDB `returning=false`（实际支持 RETURNING） | `matrix` 输出 `duckdb ... ret=false` |
| **P1** | 单元测试只断言子串，放过了非法 SQL：`assert!(sql.contains("IGNORE"))` 对 PG 的非法 `INSERT OR IGNORE` 同样通过 | `packages/sz-orm-core/src/dialect.rs:5149` |

**建议**
1. `QueryBuilder` 分页直接调用 `Dialect::build_pagination`，删除 `query.rs:2887/2891` 的硬编码；补 Oracle/MSSQL 真库断言。
2. PG 族（PG/Kingbase/PolarDB/GaussDB/CockroachDB/YugabyteDB/Redshift）实现 `build_insert_or_ignore_prefix` 返回 `INSERT INTO ... ON CONFLICT DO NOTHING`，或直接让 `insert_or_ignore` 失败并提示用 upsert。
3. `supports_lock_for_update()` 与 `build_lock_clause()` 必须一致：有支持标志就必须产出子句，否则返回错误而不是静默降级。
4. 把方言单测从“包含关键字”升级为“连真库 EXPLAIN/执行”。

### 3.2 事务语义与并发控制（15%）

**亮点**
- 保存点回滚粒度正确：实验 `savepoint` → `after savepoint rollback, row count (expect 1): I64(1)`。
- `run_transaction` 有 `catch_unwind`，panic 自动回滚再 `resume_unwind`（`packages/sz-orm-core/src/transaction.rs:520` 起）。
- 死锁识别实测有效：构造真实 MySQL 交叉 UPDATE，第二事务返回 `Deadlock found when trying to get lock`，`is_deadlock_error` 覆盖 MySQL 1213 / PG 40P01 / ORA-00060 / 1205 / SQLite locked（`packages/sz-orm-core/src/transaction.rs:427`）。
- 嵌套深度上限（默认 8）防止递归事务打爆连接（`packages/sz-orm-core/src/transaction.rs:90`）。

**风险**

| 级别 | 问题 | 证据 |
|---|---|---|
| **P0** | 隔离级别在 `BEGIN` 之后下发：MySQL 全部级别失败；SQLite 全部失败；Oracle RR/SNAPSHOT/RU 失败；PG 仅 Snapshot 失败 | `packages/sz-orm-core/src/transaction.rs:543`、`packages/sz-orm-core/src/transaction.rs:669`；实验 `iso-mysql`：`Transaction characteristics can't be changed while a transaction is in progress`；`iso-sqlite`：`near "SET": syntax error`；Oracle sqlplus：`ORA-02179: 有效选项: ISOLATION LEVEL { SERIALIZABLE | READ COMMITTED }` |
| **P0** | 设置隔离失败后直接返回 `CommitFailed`，**不回滚已开启事务**，连接被放回池（仅靠归还可疑地补救） | `packages/sz-orm-core/src/transaction.rs:543`（`?` 直接返回）；归还路径见 `packages/sz-orm-core/src/pool.rs:2059` |
| **P1** | `IsolationLevel::Snapshot` 不可移植（MySQL/PG/SQLite/Oracle 全部无此级）却作为公共枚举暴露 | `packages/sz-orm-core/src/transaction.rs:543` 拼接；实验 `iso-pg`：`syntax error at or near "SNAPSHOT"` |
| **P1** | 死锁重试是“整段闭包重放”，未提供幂等令牌/业务去重钩子；重试边界（部分语句已写）靠调用方自律 | `packages/sz-orm-core/src/transaction.rs:490` 附近重试循环 |
| **P2** | 错误类型把“隔离设置失败”归为 `CommitFailed`，误导排障 | 同上，错误文案 `SET ISOLATION LEVEL failed:` |
| **P2** | MSSQL SNAPSHOT 需要库级 `ALLOW_SNAPSHOT_ISOLATION`，代码无前置检测（无法实测，MSSQL 不可用） | 静态审查 |

**建议**
1. 在 `begin_transaction()` **之前**下发隔离级别：MySQL 用 `SET SESSION TRANSACTION ISOLATION LEVEL` 或 `START TRANSACTION ISOLATION LEVEL ...`；PG 用 `BEGIN ISOLATION LEVEL ...`；SQLite 直接拒绝非 None 隔离级别并在文档标注。
2. 隔离设置失败必须 `rollback` 后再返回，且错误类型改为 `TxError::IsolationNotSupported`。
3. 删除或 feature-gate `Snapshot`，避免用户在 PG/MySQL 上“配置成功、运行报错”。

### 3.3 连接池与连接生命周期（15%）

**亮点**
- **300 轮 acquire/close_all 竞态两库均未复现**：MySQL 侧 `rounds=300 ok_rounds=300 closed_errors=21449 UNEXPECTED_ACQUIRE_AFTER_CLOSE=0`（评测前半段 MySQL 可用时）；PG 侧重跑 `rounds=300 ok_rounds=300 closed_errors=21254 UNEXPECTED_ACQUIRE_AFTER_CLOSE=0`（日志 `/c/Users/Administrator/AppData/Local/Temp/race-pg.log`）。
- 容量与超时正确：`max=2` 持 1 个可再取（5.3ms）、持 2 个取第 3 个按 `acquire_timeout` 超时（3.016s）；`max_size=1` 第二个 acquire 1.0067s 超时，释放后可再取。
- 归还时**会回滚未提交事务**（`packages/sz-orm-core/src/pool.rs:2059`），并有关闭池/回滚失败的连接丢弃分支。
- 关闭语义：`close_all` 期间新 acquire 得到错误而非 panic（`closed_errors` 数量级 2 万，全为正常错误路径）。

**风险**

| 级别 | 问题 | 证据 |
|---|---|---|
| **P0** | **归还不重置会话状态**：`sql_mode`、用户变量、临时表跨 checkout 泄漏 | 实验 `leak`：`conn#1 set sql_mode='', @eval_marker=42, created TEMPORARY TABLE eval_tmp` → `conn#2 sees sql_mode=String("") @eval_marker=I64(42)` |
| **P1** | 双重连接池：sz-orm Pool 的 factory 内部再包 sqlx Pool，容量放大与超时叠加缺少显式换算校验 | 构造函数与 factory 组合（实验工程 `mysql_pool`/`pg_pool` 即为双层）；`max_size` 只约束外层 |
| **P1** | 归还跳过 `is_connected` 检查（依赖 `known_good` 快路径），网络闪断连接可能被再次借出 | `packages/sz-orm-core/src/pool.rs:2027` 返回路径注释“跳过 is_connected 检查” |
| **P2** | `closed_errors` 占 acquire 次数比例很高（≈2.1 万/30 万），说明关闭期背压是“刷错误”而非快速失败/排队 | 竞态实验输出 |
| **P2** | 健康检查/最大存活期行为只由 `chaos_pool` 合成连接覆盖，未在真库上做 kill 会话验证 | `cargo test -p sz-orm-core --test chaos_pool` 14 passed（合成连接） |

**建议**
1. 提供 `on_release` 会话复位（MySQL `RESET CONNECTION`/`SET SESSION sql_mode=DEFAULT`、PG `DISCARD ALL`），或至少在归还时检测 `in_transaction()` 之外的会话指纹。
2. 明确「外层池 = 唯一容量权威」，sqlx 内层池尺寸设为外层容量，避免双重排队放大 p99。

### 3.4 类型映射与数据保真（10%）

**亮点**
- BLOB/BYTEA 往返正确（`Bytes([0,1,2,250,255])` → `Bytes([0,1,2,250,255])`）。
- NULL 往返正确（PG `NULL into VARCHAR via Value::Null -> Ok(1)`；SQLite/PG 读取为 `Null`）。
- 4 字节 UTF-8 在 PG（`Value::String` + `$n`）与 MySQL 上均可写入并回读（`emoji 🚀 中文`）；MySQL 上 4 字节正常，见 `types-mysql` 输出。
- PG 普通格式 `Value::DateTime("YYYY-MM-DD HH:MM:SS.ffffff")` 能正确写入 `TIMESTAMP(6)`（DB 侧 `d::text` 证实）。

**风险**

| 级别 | 问题 | 证据 |
|---|---|---|
| **P0** | **PG 时间戳列读取恒为 NULL**（写入成功） | 实验 `(C') DB truth ts=Some("2026-10-28 12:34:56.123456")` vs `(C'') ORM read ts=Null`；解码落到未知类型分支 `packages/sz-orm-sqlx/src/any.rs:1586`（R1 后已补时间分支并改为报错） |
| **P0** | **DECIMAL/NUMERIC 双向丢精度**（38 位定点 → 28 位整数 + `.0`） | `(A) raw-exact write -> ORM read : Decimal("...5678.0")`；`(B') DB truth after ORM write : Some("...5678.0000000000")`；写入走 `rust_decimal`（`packages/sz-orm-sqlx/src/any.rs:1983`）、读取同（`packages/sz-orm-sqlx/src/any.rs:1562`） |
| **P0** | MySQL `Value::DateTime` 绑定被 `Display` 加了单引号 → SQL 里变成 `''2026-10-28 ...''` | `packages/sz-orm-core/src/value.rs:740`；实验 `types-mysql`：`Incorrect datetime value: ''2026-10-28 12:34:56.123456'' for column 'dt_col'` |
| **P1** | PG 带时区偏移的 `Value::DateTime`（`...+08`）绑定失败：解析失败后回退文本绑定，PG 报类型不匹配 | 实验 `(C) ORM ts write -> Err("column \"dz\" is of type timestamp with time zone but expression is of type text")`；回退逻辑 `packages/sz-orm-sqlx/src/any.rs:1983` 后的 `q.bind(s.as_str())` |

| **P2** | `Value::Display` 对 `String/Uuid/Date/DateTime/Time/Json` 一律加单引号，任何走 `to_string()` 的绑定路径都会中招 | `packages/sz-orm-core/src/value.rs:734`、`packages/sz-orm-core/src/value.rs:738`–`742` |

**建议**
1. PG 解码补齐 `TIMESTAMP/TIMESTAMPTZ/DATE/TIME` 分支（输出 ISO 字符串），并把“解码失败”从 `Null` 改为显式错误——**静默 NULL 是最危险的失败模式**。
2. DECIMAL 全链路改用字符串/BigDecimal（MySQL 已这么做），禁止 `rust_decimal` 的 96 位截断参与 38 位定点。
3. 绑定层禁止使用 `Value::Display` 产出 SQL 字面量；统一走参数绑定。
4. 补 4 字节 UTF-8 + 时区 + 38 位小数 + NULL 的跨库契约测试（当前测试集在 PG 上会把这些缺陷全部放过）。

### 3.5 查询性能与执行计划（10%）

**亮点**
- 公平对比（双方各持一条连接，各 2000 次，PG）：`raw sqlx : p50=196.9µs p99=278.2µs` / `sz-orm : p50=222.1µs p99=286.5µs` → **p50 开销 +12.8%，p99 +3.0%**。作为 ORM 层这个开销是合理的。
- `sz-orm-bench`（SQLite，debug）：单行查询 P50 193µs，对比 sea-orm 290µs、sqlx 222µs；批量查询 1638µs，比 sea-orm 977µs / sqlx 617µs 慢（ORM 批处理路径开销明显）。
- 预处理缓存**算法层**收益可复现：`命中率: 99.40%`、`耗时降幅: 90.7%`（`v65_prepared_cache_benefit` 实测，宣称 89.3% 基本对齐）。

**风险**

| 级别 | 问题 | 证据 |
|---|---|---|
| **P0** | **预处理缓存默认不生效**：`Connection::prepare_cached` 的唯一调用点是单元测试 | `packages/sz-orm-core/src/connection_ext.rs:200`、`packages/sz-orm-core/src/connection_ext.rs:390`（均为 `#[cfg(test)]` 内）；缓存实现 `packages/sz-orm-core/src/prepared_cache.rs:182` |
| **P1** | 唯一生产形态 `PoolElasticController` 也只被测试构造，默认 `Pool` 不使用 | `packages/sz-orm-core/src/pool_elastic.rs:1103`；`PoolElasticController::new` 仅出现在 tests（`packages/sz-orm-core/tests/v10120_pool_elastic_integration.rs:158`） |
| **P1** | N+1 运行时检测器需手动 `with_detector` 接入，默认不生效（文档措辞已降级，但仍有“检测组件”卖点） | `packages/sz-orm-core/src/entity_graph.rs:535`、`packages/sz-orm-core/src/entity_graph.rs:671`；全仓无生产调用点 |

**建议**

3. N+1 检测改为 `PoolConfig` 开关默认接入 BatchLoader。

### 3.7 迁移与 Schema 变更安全（5%）

**亮点**
- 版本表建表幂等（`CREATE TABLE IF NOT EXISTS`），迁移记录写入 `__migrations`（version/name/batch/executed_at）。
- e2e 迁移套件在 PG/SQLite 上跑通 create/alter/idempotent（`e2e_real_db_migration` 29 passed）。

**风险**

| 级别 | 问题 | 证据 |
|---|---|---|
| **P1** | 版本表**无 checksum**：已执行迁移被篡改无法发现 | `packages/sz-orm-core/src/migration.rs:422`（列只有 version/name/batch/executed_at） |
| **P1** | **无迁移并发锁**（PG advisory lock / MySQL GET_LOCK 均无）→ 多实例同时启动会并发执行 DDL | 全仓 `grep checksum|advisory|GET_LOCK` 无命中 |

| **P2** | e2e 只验证了“建表/改列/幂等”，没有“中途失败→回滚/续跑”用例 | 测试用例名 `test_e2e_pg_migration_alter_table`/`idempotent` |
| **P2** | 版本号字符串比较，回滚按版本排序假设线性历史 | `packages/sz-orm-core/src/migration.rs:647` 附近 |

**建议**
1. 版本表加 `checksum` 与 `applied_by/host`；启动时校验，漂移即拒绝。
2. 迁移前取 advisory lock（PG `pg_advisory_lock`、MySQL `GET_LOCK`），超时退出。
3. 提供 `dry-run` 仅生成 SQL，以及失败后的“人工修复记录”入口。

### 3.8 安全与多租户隔离（5%）

## 7. 与主流方案对比

| 能力 | sz-orm 10.13.0 | EF Core / Dapper | sqlpp11 / SOCI | SQLx / SeaORM / Diesel |
|---|---|---|---|---|
| 事务隔离级别 | 统一 `SET TRANSACTION`，**MySQL/SQLite 不可用**；无 per-dialect 语句 | EF Core 按 provider 生成；Dapper 透传 | SOCI 通过后端 API 设置 | SQLx `begin_with` 支持 PG/MySQL 原生语法；SeaORM 事务包装 |
| 连接池 | 自研（300 轮竞态 0 异常），**无会话复位** | ADO.NET 池成熟（`Connection Reset`） | SOCI 无内置池 | SQLx 内置池 + `after_release` 钩子可 RESET |
| 方言保真 | 28 名义 / 12 实现 / 4 真库验证；多处非法 SQL | provider 级全面 | 按后端编译期绑定 | SQLx 按后端类型安全；SeaORM 覆盖少但每条有测试 |
| 类型保真 | DECIMAL/时间戳有 P0 失真 | EF Core 全类型映射成熟；Dapper 手工 | 编译期类型安全 | SQLx 编译期 `query!` 校验列类型（最强） |
| 编译期 SQL 校验 | `query!` 宏可选连库 EXPLAIN（`db-verify`） | EF Core 迁移 + 模型校验 | 模板编译期 | SQLx `query!` 是核心卖点 |
| 预处理缓存 | 有实现、**默认未接线** | ADO.NET 自动 | 后端语句句柄 | SQLx 按连接自动 |
| 分片 / 分布式事务 | sharding 孤儿、XA Mock | EF Core 无（需外部） | 无 | SeaORM 无；SQLx 无 |
| 可观测性 | 无自动 tracing/慢查询 | EF Core 拦截器成熟 | 手工 | SQLx 有 tracing feature |
| 生态成熟度 | 自研 workspace 72 包，发布 crates.io（sz-orm-core 1.0.0） | 工业标准 | 小众但稳定 | SQLx/SeaORM 社区活跃 |

**DBA 视角**：sz-orm 在“包数量/功能清单”上对标 EF Core，但在**数据库语义正确性**上更接近早期自研 DAO。与 SQLx 相比，它牺牲了编译期类型校验，却没换来等价的语义保真。若要继续走 ORM 路线，建议直接把 SQLx `query!` 的编译期列类型校验作为默认路径，而不是可选的 `db-verify`。

## 附：三个 DBA 问题

### （1）这套东西进生产库，最可能在哪天凌晨三点叫醒我？

**PG 大表的定时报表/对账任务把 `updated_at` 读成 NULL 的那天。**
它不会报错、不会告警，只会让“最近 24 小时变更”突然变成 0 条，或者让账务对账的 `amount DECIMAL(38,10)` 全部变成 `.0000000000`。等到业务发现时，你已经无法判断是数据被删了、还是 ORM 读丢了——而这套代码不会给你任何日志线索（解码失败静默转 `Null`，`packages/sz-orm-sqlx/src/any.rs:1586` 的未知类型分支；R1 后已改为报错）。
第二顺位：MySQL 上某个服务把事务改成 `RepeatableRead` 上线，第一次写冲突时直接抛 `SET ISOLATION LEVEL failed` 并把连接带着未回滚事务还回池（`packages/sz-orm-core/src/transaction.rs:543`），随后整池被 MDL/行锁拖死。

### （2）连接池、事务、方言三类风险里，哪一类是系统性设计缺陷而非实现 bug？

**事务层。** 不是某条 SQL 写错了，而是「隔离级别 = 一条统一字符串 + 在 BEGIN 之后发送」（`packages/sz-orm-core/src/transaction.rs:543`）这个抽象本身就不成立：MySQL 要求事务特性在 BEGIN 前声明，SQLite 根本没有 `SET TRANSACTION`，Oracle 只接受两个级别，PG 的 Snapshot 不存在。同一个设计在 4 个库上产生 4 种失败形态，且失败路径没有回滚。方言层的问题是“实现漏了分支”，可以逐条补；连接池的问题是“少了一个复位钩子”，可以加上；只有事务层需要重做抽象（per-dialect 的 begin 构造器 + 能力矩阵 + 失败必回滚）。

### （3）上线前必须完成的 5 条 DBA 验收项

1. **类型保真验收**：MySQL/PG/Oracle 各建一张含 `DECIMAL(38,10)`、`TIMESTAMP(6)`、`TIMESTAMPTZ`、`DATE`、`NULL`、4 字节 UTF-8、`BLOB` 的表，写入后用 **ORM 读回**逐列断言完全相等（不是“非空即通过”）。
2. **事务隔离验收**：每库两连接脚本，分别验证 RR/RC/SER 的实际可见性；任何“设置隔离级别失败”必须让事务失败并回滚，且失败后连接可被安全复用（`SELECT 1` + `in_transaction()=false`）。
3. **方言 SQL 验收**：对目标库执行 `QueryBuilder` 生成的 分页/UPSERT/insert_or_ignore/lock_for_update 四类语句各一次，要求在真库上**执行成功且语义正确**（Oracle/MSSQL 不得出现 `LIMIT`；PG 的忽略插入必须是 `ON CONFLICT`；`FOR UPDATE` 必须真的出现在 SQL 里）。
4. **连接池卫生验收**：连接 1 设置 `sql_mode`/`search_path`/临时表后归还，连接 2 必须看不到；kill 掉一个后端会话后，池能在 `acquire_timeout` 内自愈且不把死连接借出。
5. **发布安全验收**：迁移带 checksum 与并发锁；两实例同时启动迁移一成一等；已执行迁移被篡改时启动必须拒绝。e2e 套件在缺少数据库时**必须红**，不允许静默 `ok`。

### 11.2 关键说明与新增发现

- **R1 扩展到 MySQL（本轮新发现）**：报告原条目只覆盖 PG，但补写「MySQL DATE/DATETIME/TIME 精确断言」时真库复现了同类缺陷——MySQL 二进制协议下按 `String` 解码时间列必然失败，旧实现经 `row_to_value_mysql` / `row_to_value_with_coltype_mysql` 静默返回 `Null`。已在两个解码器补齐 `NaiveDate/NaiveDateTime/NaiveTime` 分支（`packages/sz-orm-sqlx/src/any.rs:762`、`:918`），并保留字符串回退。
- **R2 MySQL 路径**：`Value::Decimal` 参数以字符串绑定（`packages/sz-orm-sqlx/src/any.rs:890` 解码、`packages/sz-orm-sqlx/src/any.rs:1983` PG 绑定），避免 `rust_decimal` 28 位上限截断；38 位 `DECIMAL(38,0)` 真库往返逐位一致。
- **R3 断言方式**：MySQL 一次性 `SET TRANSACTION`（无 `SESSION` 作用域）不改变 `@@transaction_isolation` 会话变量，故不能用会话变量断言；改为可观察行为差分——同一测试内默认 RR 得 `(1, 1)`，显式 READ COMMITTED 得 `(2, 3)`，证明隔离级别确实作用于**当前**事务。
- **R6 严格模式验证**：为证明「缺库不再静默通过」，分别执行默认模式与严格模式；严格模式对必需 service 的 3 个 MySQL 用例按设计失败，这是门禁语义正确的证据，不是回归。
- **R9 语义**：默认 `TenantScope` 对未设置租户上下文的模型追加恒假条件 `1 = 0`（返回空集）；需要跨租户时必须显式 `without_tenant()`，或用兼容作用域 `PermissiveTenantScope`（`packages/sz-orm-core/src/hooks.rs:544`）。启用 `multi-tenant-enhanced` 时无上下文直接 panic（fail-closed）。

### 11.6 R8 实测：预处理语句缓存开/关的端到端 p50（2026-10-29）

**测量对象**：Oracle 23ai Free 上的点查（`SELECT id FROM t WHERE id = :1`，主键命中 1 行），release 构建。开/关由 `stmt_cache_size(256)` 与 `(0)` 控制；每侧预热 200 次、每轮 1000 次采样、开/关交替 5 轮、取各轮 p50 的中位数。

**三层测量**（同一台机器、同一轮运行）：

| 层 | 关闭 p50 | 开启 p50 | 降幅 |
|---|---|---|---|
| 驱动层（`oracle::Connection::query`） | 255.7 µs | 178.0 µs | **30.4%** |
| 端到端（sz-orm Oracle 适配器 `query_with_params`） | 303.7 µs | 227.4 µs | **25.1%** |
| 端到端 + 8 会话并发 | 342.4 µs | 252.1 µs | **26.4%** |

同一命令复跑三次，端到端降幅分别为 27.9%、31.8%、25.1%，驱动层为 28.0%、31.4%、30.4%——**区间 25.1%–31.8%，中位数约 28%**，围绕 30% 验收线上下波动。

**为什么是 ~30% 而不是更高**：OCI 语句缓存省去的是**一次 prepare 往返**（本机实测约 73–84 µs）。一次查询的 p50 = prepare 往返 + 执行/取数（约 100–110 µs）+ 适配器固定开销（约 48–70 µs，主要是阻塞线程跳转）。prepare 占比较小，是缓存收益的上限；理论上限为 50%（两次往返省一次）。在跨网络的部署中，RTT 远大于本地取数开销，省下的一次往返占比会显著上升并逼近该上限——本报告不为此给出未实测的数字。

**适配器层的定位（不变）**：池级 `PreparedStatementCache` 对 sqlx 后端仍是"记账层"（sqlx 在物理连接内部已缓存语句，`pool.rs:3172` 断言了未命中语义）；对 tiberius 0.12，驱动只有 sp_executesql（`RpcProcId::ExecuteSQL`），没有 prepared handle API。因此真实可用的预处理复用杠杆是 Oracle 的 OCI 语句缓存，现已默认启用（20，OCI 默认值，避免超出 `open_cursors`），并可由 `SZ_ORM_ORACLE_STMT_CACHE_SIZE` 调优、由 `SZ_ORM_PREPARED_CACHE=0` 统一关闭用于 A/B。

**文档修正**：README 原称 `PreparedStatementCache` 命中收益 "≥ 50% latency reduction"，与实测不符，已改为实测区间并标注测量范围；CHANGELOG 中 89.3% 是**算法级**基准（SQLite prepare vs 缓存查找，非端到端），已加注说明。
