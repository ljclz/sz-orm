# 三、转正 / 废弃建议

## 3.1 推荐：**转正（保留）**，但缩小范围、分两阶段

**理由**：
1. **缓存下推 + 降级语义验证充分**（4 个测试直接覆盖），实现成本低（~400 LOC），
   与既有 `sz-orm-adaptive`（M4）形成互补：M4 解决"何时用缓存"，fusion 解决"缓存键如何下推"
2. 确定性缓存键设计（等值条件排序）可安全推广——**不改变主库查询语义**，
   主库步骤始终存在，缓存仅加速
3. 降级路径（主库失败回退）是生产高可用刚需，POC 已验证标记语义

**风险与限制（转正前必须解决）**：
1. **一致性**：缓存 TTL 缺失（MemoryFusionCache 无过期），转正需 TTL + 失效广播
   （复用既有 `l2_cache.rs` 的 `InvalidationBus`）
2. **数据同步**：主库 → 缓存/搜索索引的增量同步未实现（POC 未接既有 CDC
   `packages/sz-orm-queue/src/cdc/capturer.rs:12`），转正阶段一可暂用 TTL 过期兜底
3. **搜索下推**：当前仅为"源标记"，真实向量检索需集成 `sz-orm-vector` 混合搜索
   （`searcher.rs:30`），建议转正阶段二再做

## 3.2 转正路线（两阶段）

| 阶段 | 内容 | 工作量 | 前置 |
|------|------|--------|------|
| 阶段一（v4.3.x） | TTL 缓存 + 失效广播（适配既有 l2_cache）+ 缓存下推转正式 API | 2 周 | 无 |
| 阶段二（v4.4.x） | CDC 增量同步 + 真实向量搜索下推 | 3 周 | 阶段一 |

## 3.3 废弃条件

若阶段一完成后**无真实业务场景使用**（sz-pay 或试点项目未采用），
建议降级为示例代码（examples/）保留模式，不再维护为正式包。

# 四、结论

**多数据库融合查询方向可行，POC 通过**：缓存下推 + 主库降级语义已代码验证。
推荐**转正（阶段一）**：TTL + 失效广播 + 正式 API；真实搜索下推与 CDC 同步
放阶段二。若阶段一无采用则降级为示例。
