## 七、关键发现

### 7.1 连接池设计存在根本缺陷

Oracle 与 MSSQL 适配器名义上是"连接池"，实际是单连接 + Mutex 串行化，与 sz-orm-core 的 Pool（真正的多连接池）形成断层。**这是最严重的 P0 问题**。

### 7.2 生产 unwrap() 泛滥

L2Cache、Repository、EntityGraph 等核心模块共 **30+ 处 unwrap()**，任一 panic 会导致模块永久中毒（RwLock/Mutex poisoned），无法降级。

### 7.3 类型映射优化形同虚设

`ColType` 枚举已定义（`value.rs:479-520`）但 SQLx 适配器未使用，每行每列仍做字符串 match。之前声称的性能优化实际未生效。

### 7.4 基准测试覆盖不足

无内存分配分析、无火焰图、无 P99 延迟分布，无法支撑性能回归检测。bench 内 `block_on` 污染测量数据。

### 7.5 SQLite 生产配置缺失

WAL/busy_timeout 仅在测试中配置，生产路径使用默认配置，高并发下会频繁 `SQLITE_BUSY`。

### 7.6 模块间集成度不足

audit/masking/observability/health/limit 等模块作为独立组件存在，但未与 ORM 核心执行路径自动集成。业务方需要大量手写胶水代码才能让这些能力生效，违反"开箱即用"原则。

### 7.7 安全运维能力薄弱

行级/字段级权限、SQL 防火墙、TLS 连接加密、密钥轮换全部缺失。对于企业级生产部署，这些是基本要求。

### 7.8 资源治理能力薄弱

内存限制、查询超时、结果集大小限制、慢查询自动 Kill 全部缺失。单个查询可能耗尽进程内存或连接池。

## 八、修复优先级建议

### 第一优先级：P0 阻断级（11 项）
- 修复 Oracle/MSSQL 单连接伪池（#2, #3）
- 修复 `PooledConnection` 非 tokio runtime drop 泄漏（#4）
- 修复 GraphQL `block_on` 死锁风险（#1）
- Connection trait 增加 prepared statement 支持（#5）
- WHERE 条件改为参数化绑定（#6）
- CLI `migrate` 命令支持 DSN 执行（#7）
- L2Cache 增加 Redis 后端（#8）
- `sql_type_to_rust` 改为精确匹配（#9）
- 提供 axum/actix extractor（#10, #11）

- SQL 防火墙（#53）

- 内存限制、查询超时、结果集限制、慢查询 Kill（#56, #57, #96, #97）
- 优雅停机（#50）
- Prometheus exporter + 健康检查 HTTP 端点（#48, #49）

### 第三优先级：P1 性能与可靠性（30 项）
- 流式查询（#14, #25）
- 批量操作（#26）
- 替换生产 unwrap() 为 expect()（#16, #17, #18）
- NUMERIC/DECIMAL 精度保留（#19, #20）
- SQLite WAL 生产配置（#21, #22）
- Oracle Array DML（#22）
- 事务超时（#44）

### 第四优先级：P2 中等级（40 项）
- 连接池动态缩放、预热、指数退避

- L2Cache LRU O(1) 优化

### 结论
